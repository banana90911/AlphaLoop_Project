## 8. 대시보드

시스템/자본 상태를 확인하는 도구

### 8.1 지켜야 할 경계

- 읽기 전용

### 8.2 "최신 상태"의 정의

- 브라우저가 60초마다 API를 다시 호출해 화면을 갱신한다. 페이지 전체를 새로 그리지 않고 바뀐 값만 다시 그린다.
- 화면 상단에 마지막 업데이트 시간 표시

### 8.3 기술

**확정 ① — 백엔드는 `FastAPI` + `uvicorn`.** SQLite를 읽기 전용(`mode=ro`)으로 열어 SELECT 결과를 JSON으로 돌려주고 프론트 파일을 함께 서빙하는, 얇은 읽기 계층이다. `GET`만 존재하고 쓰기 경로 자체가 없다(8.1 불변식). ORM·인증·세션·서버사이드 렌더링은 두지 않는다. 조회 결과의 표·주월 집계 가공은 `pandas`로 서버 쪽에서 한다.

**확정 ② — Streamlit은 쓰지 않는다.** 상호작용이 있을 때마다 스크립트를 처음부터 다시 실행하는 모델이라, 8.4 ③의 *한 행을 고르면 같은 자리에서 근거가 펼쳐지는* 화면이 부자연스럽다. 배치도 위젯이 정한 틀을 크게 벗어나기 어렵다. 매일 들여다보는 복기 도구이므로 화면을 우리가 정할 수 있어야 한다.

**미정 — 프론트를 무엇으로 만들지.** 정하지 않았다. 후보와 판단 기준만 적어둔다.


| 후보                   | 좋은 점                                           | 치르는 비용                                                   |
| -------------------- | ---------------------------------------------- | -------------------------------------------------------- |
| React(+Vite)         | 목록·펼침·필터 같은 상태를 다루기 가장 편하고, 표·차트 라이브러리 선택지가 넓다 | npm·빌드 단계가 생긴다(서버에 Node는 필요 없다 — 빌드 결과가 정적 파일이라 그것만 올린다) |
| 바닐라 HTML·CSS·JS      | 빌드가 없다. 파일 저장 후 새로고침이 전부                       | 표 정렬·필터·펼침을 직접 만들어야 한다                                   |
| htmx·Alpine.js 같은 경량 | 빌드 없이 부분 갱신·상태를 얻는다                            | 화면이 복잡해질수록 오히려 흐름을 쫓기 어려워질 수 있다                          |


판단 기준은 셋 — ⑴ 8.4 ③ 드릴다운을 자연스럽게 만들 수 있는가, ⑵ 1인이 몇 년 뒤에도 고칠 수 있는가, ⑶ 산출물이 정적 파일이라 FastAPI가 그대로 서빙할 수 있는가.

어느 쪽을 골라도 **백엔드 계약(GET + JSON)은 바뀌지 않는다.** 그래서 API를 먼저 만들고 프론트 결정은 뒤로 미뤄도 되고, 나중에 갈아엎어도 백엔드는 그대로다.

차트 라이브러리도 프론트를 정한 뒤에 고른다(plotly.js·ECharts·uPlot 등). 공통 조건 하나만 미리 못 박는다 — **라이브러리 파일을 저장소에 넣어두고 로컬에서 불러온다.** 사설망이라 CDN에 못 닿고, 외부 요청 0이 원칙이다.

### 8.4 화면 구성

네 영역을 **한 페이지**에 놓는다. 페이지 이동이나 탭 전환 없이 스크롤만으로 전부 본다.

```
┌──────────────────────────────────────────────────────────────┐
│ ④ 알림 띠 — 지금 정지 중인가 / 어제 배치가 깨졌나                      │
├────────────────────────────────────┬─────────────────────────┤
│                                    │ ① 계좌 현황 (2×2 칸)    │
│ ② 자본 곡선 + 벤치마크             │    총자본·예수금·       │
│    (왼쪽 위에 현재 총자본 큰 숫자, │    평가손익·수익률      │
│     오른쪽 위에 기간 토글)         ├─────────────────────────┤
│                                    │ ① 보유 종목 (n)         │
│                                    │    한 줄에 한 종목       │
├────────────────────────────────────┴─────────────────────────┤
│ ③ 거래 리포트 — 표에서 한 줄을 고르면 그 자리에서 근거 펼침  │
└──────────────────────────────────────────────────────────────┘
```

- 값이 오르면 초록, 내리면 빨강으로 통일한다(국내 HTS의 빨강=상승과 반대이므로 헷갈리지 않게 한 규칙만 쓴다).
- **보유 0종목·거래 0건인 날이 정상이다.** 종목당 한도와 1주 단위 때문에 실제 보유는 대개 2~4종목이고 아예 없는 날도 흔하다. 빈 화면이 고장처럼 보이지 않게, 각 영역은 "보유 없음 — 마지막 사이클 HH:MM 정상 종료" 같은 문장을 자리에 채운다.

**① 나의 정보 — 잔고·보유 종목·평가손익**

- 계좌 현황은 네 칸 — **총자본·예수금·평가손익·당일 손익률**. 현금·총자본·당일 손익률은 `AccountSnapshots`의 마지막 행에서 온다.
- 평가손익: `Positions.averagePrice` vs 마지막 사이클이 본 가격(`CycleScores.lastPrice`). 틱 단위 현재가가 아니라 마지막 사이클 기준이다. 그래서 네 칸 아래에 그 사이클 시각을 작게 적어, 이 숫자가 언제 기준인지 오해하지 않게 한다.
- 보유 종목은 한 줄에 한 종목 — 종목명, 오른쪽에 수익률(색), 아랫줄에 평단·보유일수·수량. `Positions`(`status='open'`)에서 직접 온다.
- 여기에 **손절가를 한 줄에 같이 적는다.** 이 시스템에서 매 순간 가장 중요한 숫자가 손절가이고(5장), 지금 가격이 손절가에서 얼마나 떨어져 있는지가 보유 종목을 볼 때 제일 먼저 확인할 것이기 때문이다.
- 거래정지로 동결된 보유(`status='frozen'`)는 동결가로 합산해 자본곡선이 흔들리지 않게 하고, 그 줄에 "동결" 표시를 붙여 평가손익이 멈춘 이유를 드러낸다.
- 종목이 많아 넘칠 때만 "더보기"로 접는다. 대개는 접을 일이 없다.

**② 수익 곡선 — 시간순 누적 + 벤치마크**

- 자본곡선: `Outcomes.netProfitLoss`(비용 차감 후 실현손익)를 청산일 순으로 누적. **성과 판단은 이 선 하나로만 한다.**
- 왼쪽 위 큰 숫자는 지금 총자본(`AccountSnapshots` 마지막 행). 눈에 먼저 들어오는 자리라 "지금 얼마인가"를 여기서 끝낸다. 곡선과 다른 값이라는 점이 헷갈릴 수 있으므로, 평가액을 포함한 일별 총자본 곡선은 **토글로 겹쳐 볼 수만 있게** 하고 기본은 꺼둔다.
- 호버 툴팁: 그 거래의 날짜·종목·실현손익·R 배수(`rMultiple`).
- 곡선 위에 매수·매도 시점을 점으로 찍는다(초록·빨강). 어느 구간의 상승이 어느 거래에서 나왔는지 눈으로 잇는 용도다.
- 벤치마크 겹쳐 그리기: `MarketIndices`의 코스피·코스닥 + 균등가중 워치리스트(9장 벤치마크와 같은 산식). 우리 전략이 비용 떼고 이들을 이기는지 한눈에 본다. **이 선들은 기본으로 켜 둔다** — 우리 곡선만 보면 상승장을 실력으로 착각하기 때문이다.
- 기간 토글은 **3개월·1년·전체**. 사이클이 하루 한 번이라 하루 안을 확대할 것이 없으므로 "일" 단위 토글은 두지 않는다.

**③ 거래 리포트 — 목록 + 근거 펼침**

거래를 한 줄 요약으로 쭉 보여주고, 한 줄을 고르면 그 거래를 왜 했는지가 같은 화면 아래에 펼쳐진다. 별도 상세 페이지로 이동하지 않는다.

- 목록: `Orders`·`Positions`·`Outcomes`를 시간순으로 한 행씩. 열은 **날짜·시각·구분(매수/매도)·종목(+종목코드)·단가·수량·거래대금·손절가·상태(보유/청산)**. 날짜 필터와 전체/매수/매도 토글로 좁힌다.
- 거래대금은 매수면 음수(빨강), 매도면 양수(초록)로 부호를 붙여 현금이 어느 쪽으로 움직였는지 바로 읽히게 한다.
- 펼침 — 진입 근거: `Decisions`의 점수·적용 임계·손절가·R·위험 비율·수량·기대 엣지, `CycleScores`의 항목별 백분위(모멘텀·수급·거래대금·정배열·저변동성)와 레짐.
- 펼침 — 게이트 결과: `RiskChecks`에서 어느 관문에 걸려 거부·축소됐는지.
- 펼침 — 청산 결과: `Outcomes`의 실현손익·보유일수·청산 사유(`exitReason`).
- 이 근거들은 전부 숫자라 행 크기가 작다. 압축·삭제 없이 영구 보존하므로 몇 년 전 거래도 근거가 그대로 남는다.

**④ 오류·정지 알림**

- `SafeStopEvents` — 발생 시각·원인·해제 여부. 비어 있는 `releasedDateTime`이 곧 "지금 정지 중"이다.
- `Cycles` — `failed`·`skipped` 사이클과 실패 단계.
- `IngestRuns` — 일일 배치 결과. `failed`·`partial`이면 그날 데이터가 낡았다는 뜻이라 눈에 띄게 표시한다.
- 행을 고르면 원인과 무엇을 확인하고 어떻게 해제하는지를 함께 보여준다. 잔고 불일치·데이터 오류는 사람 개입 해제가 필수다(5.3).
- 대시보드는 읽기 전용이라 해제 버튼을 누르는 곳이 아니다 — 무엇을 해야 하는지 알려주는 곳이다.

### 8.5 어디서 읽고 어떻게 접속하나

- 매매 cron과 대시보드를 **같은 상시 서버**에서 돌리고, 서버 로컬 디스크의 `journal.sqlite`를 직접 읽는다. WAL 모드라 매매 코어가 쓰는 중에도 동시 읽기가 된다.
- 접속은 **SSH 포트포워딩** 또는 **Tailscale**(내 계정 기기끼리만 잇는 사설망)로 내 기기에서만. 공개 인터넷 노출은 0이다.
- `uvicorn`은 `127.0.0.1`에만 바인딩한다. 서버 밖에서는 포트 자체가 안 보이므로 위 사설 경로 말고는 닿을 방법이 없고, 그래서 로그인 인증을 만들 필요도 없다.
- 공개 배포를 하지 않는 이유는 셋이다 — 로그인 인증을 직접 만들어야 하고, 자본시장법상 공개 표면이 생기고, 비용·운영이 늘어난다. 사설 접속이면 이 부담 없이 "어디서나"를 얻는다.
- 호스트가 바뀌어도(서버 → 맥미니) 대시보드 코드는 그대로다. DB 경로 설정만 바뀐다.
