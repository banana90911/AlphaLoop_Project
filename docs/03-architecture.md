## 3. 시스템 아키텍처

한 사이클의 흐름은 *코드가 후보·데이터·기억을 준비 → LLM이 분석·반박·결정 → 코드가 검증·집행·기록*이다. 외부 스케줄러가 정해진시각에 한개의 코드를 실행하면 아래 8단계가 차례로 돌고, 결과는 전부 SQLite에 남는다. 거래 데이터는 대시보드로 확인할 수 있다.

### 3.1 사이클 8단계 (평일 정기 2회 + 이벤트 즉시 실행)

사이클은 두 종류로 돈다. *정기 사이클*은 평일 정해진 시각에 자동으로 두 번 돌고, *이벤트 트리거 사이클*은 정기 사이클 사이에 *예측 불가능한 시점*에 새 정보가 도착했을 때 즉시 한 번 더 돈다. 두 종류 모두 아래 8단계를 동일하게 수행한다 — 다른 코드가 아니라 *같은 코드가 다른 시각에 트리거되는 것*이다.

```markdown
LLM(에이전트)를 사용하는 경우와 사용하지 않는 경우 테스트 필요.

테스트 분기
1. 결정 에이전트 사용
   - 정기 2회(10:00 & 14:30) + 30분 이벤트트리거사이클 (10:30, 11:00, ..., 14:00)
2. 결정 에이전트 미사용
   - 정기 30분마다 (10:00, 10:30, ..., 14:30)
```

**정기 사이클 — 오전 10:00 & 오후 14:30** 두 시각 모두 *그 직전에 시장에 들어온 새 정보*가 다음 결정에 가장 잘 반영되는 지점이다.

- **10:00 사이클**:  
① 어젯밤 미국장 마감(한국시간 새벽 6시) 정보의 신선도가 가장 높은 시점이라 글로벌·매크로 신호의 핵심 입력이 가장 잘 활용된다.  
② 외국인 매매가 개장 직후 10시 사이에 집중되는 한국장 특성상, 그 초기 흐름이 반영된 상태에서 수급 신호를 본다.  
③ 09:00~10:00 개장 변동성 구간은 정기 사이클이 안 도는 시간이라 별도 그레이스 윈도우 없이도 노이즈가 자연스레 회피된다.
- **14:30 사이클**:  
④ 장 마감(15:30)까지 1시간 여유로, 그날의 *외국인·기관 누적 순매수가 어느 정도 굳어진 상태*에서 보유 포지션을 재평가한다 — 10시 시점에는 잠정치만 보였던 수급 신호가 14:30에는 훨씬 또렷해진다.  
⑤ 미국 야간 선물·환율의 *오후 흐름* 변화(한국 시간 13시 이후 미국 선물 거래량이 늘기 시작)가 한국장에 영향을 미치기 시작하는 시점이라 글로벌·매크로 신호 갱신 가치가 크다.  
⑥ 14:50~15:30 동시호가·마감 구간은 사이클이 안 도는 시간이라 마감 직전의 단일가 노이즈를 피한다.

두 정기 사이클 사이에는 *방치 시간*이 존재한다 — 10:00→14:30 사이의 **4시간 30분**, 14:30→다음날 10:00 사이의 **19시간 30분**(장 마감 후 + 야간 미국장 + 다음날 개장 갭 포함). 이 방치 시간 동안 보유 종목이 손절선에 닿아도 우리 시스템은 아무 동작을 하지 못하므로, **손절 메커니즘(스톱지정가 주문)을 KIS에 미리 등록**해 우리가 깨어 있지 않아도 손절선 도달 즉시 KIS가 자동 체결되게 한다.

**이벤트 트리거 사이클**  
정기 사이클 2회만으로는 *시각을 예측할 수 없는 급변 정보*에 대응할 수 없다. 이 공백을 메우기 위해, *보유 종목*에 다음 이벤트가 발생하면 *즉시* 사이클을 한 번 더 돌린다.  
**이벤트 트리거는 보유 종목 방어 전용이다** — 워치리스트(신규 매수 후보)는 감시하지 않는다. 이벤트 사이클이 어차피 신규 진입을 하지 않으므로(아래 *출력·데이터 범위*), 워치리스트를 감시·수집하는 것은 토큰만 쓰고 행동으로 이어지지 않기 때문이다.

*포착 방식은 단계적이다 — 현재는 폴링, 상시 환경 확보 시 WebSocket.*

- **현 단계(폴링)**: 상시 켜진 서버 없이, 장중(09:00-15:30) 30분 간격으로 가벼운 감시 코드가 깨어나 보유 종목의 가격을 확인한다. *감시 자체는 LLM을 부르지 않으므로 토큰을 쓰지 않는다* — 조건을 통과해 사이클을 실제로 깨울 때만 토큰이 든다. 폴링 단계의 트리거는 **가격 기반 두 종류**이다.
  - **급변 트리거**: 보유 종목 현재가가 *직전 사이클이 그 종목을 본 가격(기준가) 대비 ±X%(config, 기본 ±5%)* 이상 변동할 때. 손절선 자체는 이미 KIS에 스톱지정가로 박혀 있지만, *손절 이전에라도* LLM이 논지 재평가를 할 가치가 있는 폭이다.
  - **손절 구멍 트리거**: 보유 종목 현재가가 KIS에 등록된 *스톱 트리거 가격을 이미 이탈*했는데도 잔고에 *미체결로 남아 있을* 때 — 개장 갭이 지정가를 건너뛰어 스톱지정가가 무력화된 상황이다. 특히 *개장 첫 폴링(09:00~)*이 밤사이 갭으로 뚫린 손절 구멍을 잡는 지점이다. 이 트리거가 깨우는 이벤트 사이클은 신규 진입 없이 *미체결 스톱을 시장가로 강제 정리*만 수행해, 정기 10:00 사이클을 기다리며 09:00~~10:00 갭이 방치되던 구간을 좁힌다. 급변 트리거(±5%)와 달리 *종목별 실제 손절가 이탈*로 판정하므로 손절폭이 5%보다 좁은 종목의 갭도 정확히 포착한다. **이 트리거는 손실 방어 필수라 아래 이벤트 사이클 일일 상한(기본 10회)의 예외로, 상한 도달 후에도 실행이 보장된다.**

*출력·데이터 범위 — 보유 재평가로 한정, 스크리닝 생략.*
이벤트 트리거 사이클의 출력은 **보유 포지션 재평가에 한정**한다 — 즉 *논지 무효 강제 청산·트레일링 조정·부분 청산* 같은 보유 종목 관련 결정만 내릴 수 있고, 신규 진입 후보는 다음 정기 사이클로 미룬다. 그래서 이벤트 사이클은 8단계 중 **1단계(후보 선별)의 KRX 전 종목 스크리닝을 건너뛰고 워치리스트 = 보유 종목(+트리거 친 종목)으로 좁힌다.** 

범위를 좁히는 두 이유:  
ⓐ 이벤트는 *기존 보유 종목과 관련된 정보*인 경우가 많아 신규 진입 판단에 필요한 워치리스트·매크로 컨텍스트가 신선하지 않다.  
ⓑ 이벤트 트리거가 폭주하면 LLM 호출 비용이 통제 불능으로 늘 수 있어, 출력·데이터 범위를 좁혀 호출당 비용·복잡도를 묶어둔다.

같은 이벤트가 단시간 내 여러 번 발생해도 한 번만 사이클을 돌린다. 또한 *이벤트 사이클 일일 총 횟수 상한*(기본 10회, config)을 두어 *비용 폭주 시 자동 차단*한다 — 상한 도달 시 그 날 남은 이벤트는 다음 정기 사이클까지 누적해 일괄 처리한다. **이 상한은 이벤트 사이클에만 적용되며, 정기 2회(10:00·14:30)는 어떤 경우에도 실행이 보장된다** — 토큰·비용이 부족해지는 상황에서 미뤄지는 것은 *이벤트 사이클*이지 정기 사이클이 아니다(정기 사이클이 결정의 1차 축이라는 우선순위).

**추가 확장(정기 3회 이상)은 백테스트와 모의 데이터가 비용 대비 효과를 정당화한 후에 검토**한다. 이벤트 트리거가 *예측 불가능한 시점*을 이미 커버하므로, 단순히 정기 사이클을 늘리는 것은 우선순위가 낮다.

**사이클 8단계**

1. **후보 선별 (코드)** — KRX 전 종목에서 거래정지·관리종목·우선주처럼 매매 부적합 종목을 제외 필터로 빼고, 거래대금 하한 같은 포함 필터를 통과시킨 뒤, 모멘텀·수급·거래대금 점수로 줄세워 상위 N개를 뽑는다. 여기에 *현재 보유 종목*을 합친 것이 이번 사이클의 *워치리스트*이다.

```
워치리스트 선정 기준 (모멘텀, 수급, 거래대금, 정배열, 저변동성의 가중치) 정립 필요.
```

2. **데이터 수집 (코드)** — 워치리스트 종목에 대해 국내 시세·수급(KIS/KRX: 계좌·잔고·시세·기술지표·수급·시장 레짐), 글로벌·매크로(yfinance·FRED: 미국 증시·환율·금리), 이벤트 캘린더(실적·FOMC·옵션만기·지수 리밸런싱·락업 해제 등)를 끌어와 정돈한다.
3. **기억 검색 (코드)** — SQLite 저널에서 *오늘과 닮은 과거 상황과 교훈*을 인출한다. **단 교훈은 회고 에이전트가 쓰는데 회고가 초기 보류라, 초기엔 교훈이 비어 이 단계가 사실상 휴면** — 그 시기 실제로 작동하는 학습은 5번 결정 단계에 주입되는 보정통계(코드 산출)뿐이다. 인출 스코어러는 구현해 두되 빈 결과를 정상으로 처리하고, 회고 도입 후 교훈이 쌓이며 활성화된다.

```
결정에이전트를 사용하지 않을 경우, 회고 에이전트 또한 사용하지 않음. 회고록이 없어도 레짐 데이터는 저장됨.
```

4. **뉴스·촉매 분석 (LLM)** — 워치리스트 종목의 뉴스 헤드라인·공시 본문·추정실적/목표주가/투자의견을 *한 번에 묶어* 읽고 "왜 지금 움직이나(촉매)"를 판단한다. 공시 본문은 *같은 이 에이전트의 입력*이라 별도 분석가를 만들지 않으며, 장문 압축 전처리가 필요해 헤드라인보다 늦게 합류한다. 헤드라인 *수집*은 코드·종목별·무료(네이버 검색 API), *판단*만 LLM 묶음 1회.

```
뉴스/공시 에이전트는 고도화로 분류.
```

5. **결정 에이전트 (LLM)** — 코드 산출 숫자 점수 + 4번 촉매 판단 + 교훈검색 + 보정통계 + 리스크제약 + 보유현황을 받아 *코드가 그대로 읽을 수 있는 JSON 제안 주문*을 낸다. *반대 시나리오 검토는 별도 호출·별도 단계 없이 이 지시문 안에 규칙으로 포함한다*. **이 에이전트의 존속 자체가 조건부다**. 두 종류를 함께 결정한다:
  - *신규 진입*: 종목·수량·손절·익절·청산 계획
  - *보유 포지션 동적 관리*: 이미 들고 있는 종목 각각에 대해 다음 중 무엇을할지
    - *트레일링*: 가격이 오른 만큼 손절선을 끌어올려 수익을 점진적으로 굳히기
    - *분할 청산*: 가격대별로 나눠 일부 매도
    - *시간 기반 청산*: 매수 후 N일이 지나면 가격과 무관하게 정리(매수 논거의 답이 안 나오면 자본 회수)
    - *논지 무효 강제 청산*: 매수 이유 자체가 사라지면 손익에 무관하게 즉시 정리

```
매매 판단에 결정에이전트 사용여부는 백테스트로 결정. 코드로 판단 시 기준 정립 필요. (과거 비슷한 레짐 데이터 반영 기준 포함)
```

6. **리스크 검증 (코드)** — LLM 제안을 그대로 실행하지 않고 다음을 차례로 통과시킨다:
  - *선행 게이트(잔고 정합성 대조)*: SQLite의 내부 잔고·포지션이 KIS 실잔고와 일치하는지 가장 먼저 확인. 어긋나면 그 자리에서 사이클 중단
  - *하드룰*: 종목당 최대 비중·전체 노출 한도·일일 매매 횟수 등 위반 시 거부 또는 축소
  - *비상 정지 트리거(서킷브레이커)*: 일일 손실 한도·모델 이상행동·API 오류율 급증 등 비상 신호 시 강제 정지
7. **주문 실행 (코드)** — KIS API로 주문 송출. *손절은 KIS에 스톱지정가 주문으로 등록*하여 우리 시스템이 꺼져 있어도 손절선 도달 시 자동 체결되게 한다.
8. **기록 (코드)** — 이번 사이클의 입력 컨텍스트, 뉴스 분석가 견해, 결정 JSON(반대 시나리오 검토 반영분 포함), 리스크 게이트 결과, 체결 까지 *전부* SQLite에 남긴다(학습 루프의 기록, 측정·감사의 1차 자료).



### 3.2 사이클 밖에서 도는 두 프로세스

- **회고 에이전트 (LLM) — 초기 보류**: 사이클과 별개로 *장 마감 후·주간·청산 시점*에 *예측 vs 실제*를 비교해 *말로 된 교훈*을 작성·저장하는 프로세스이다. **그러나 돈에 영향을 주는 학습(보정통계 → 사이징)은 전부 코드(SQL)가 하므로 회고 없이도 학습 루프는 닫힌다.**

```markdown
결정에이전트를 사용하지 않을 경우, 회고 에이전트 또한 사용하지 않음.
```

- **Streamlit 대시보드** — 매매와 분리된 *읽기 전용* 프로세스. 같은 SQLite를 읽어 수익·포지션·매매내역·결정 근거·교훈을 시각화한다. 매매와 대시보드는 서로의 가동 여부에 의존하지 않는다(한쪽이 죽어도 다른 쪽은 돈다).

```markdown
프론트 java, react, ... 사용여부 판단 필요.
```



## 3-2. 에이전트 구성

**대원칙: 코드는 숫자·규칙·리스크·통계를 하고, LLM은 비정형 데이터 사용 시에만 쓴다.** 지표·수급·매크로·섹터 상대강도·레짐은 코드가 계산하므로, 그 숫자를 *말로 다시 설명*하는 LLM 분석가(기술·수급·매크로·포트폴리오)는 두지 않는다 — 비용·환각만 더하고 새 정보가 없다.


| #   | 에이전트          | 모델     | 입력                                                                                     | 역할                                                                                                                      | 상태                       |
| --- | ------------- | ------ | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| 1   | **뉴스·촉매 분석가** | Sonnet | 뉴스 헤드라인 + 공시 본문(헤드라인 다음 합류) + 추정실적·목표주가·투자의견                                         | "왜 지금 오르나(촉매)"를 *글*에서 읽어 판단. 워치리스트 종목 헤드라인을 *한 번에 묶어* 호출(종목당 호출 아님). 신호별 출처 라벨(news/disclosure/fundamental)로 사후 공헌도 귀속. | **보류 - 고도화**             |
| 2   | **결정 에이전트**   | Opus   | 코드 산출 숫자 점수(스크리닝·지표·수급·매크로·섹터강도·레짐·이벤트캘린더 플래그) + 1번 촉매 판단 + 교훈검색 + 보정통계 + 리스크제약 + 보유현황 | 구조화 JSON 제안주문(신규 진입 + 보유 동적 관리). *반대 시나리오(악마의 변호인)는 별도 호출 없이 이 지시문에 포함*.                                                | **조건부** — 백테스트 3자 비교로 검증 |
| 3   | 회고 에이전트       | Sonnet | 예측 vs 실제 손익                                                                            | 교훈을 *글로* 작성 → 저널.                                                                                                       | **보류 - 고도화**             |


- **왜 분석가를 뉴스 1명으로 줄였나**: 기술·수급·매크로·포트폴리오 신호는 전부 *숫자*라 코드가 계산해 결정 에이전트에 직접 넣으면 된다. LLM이 "RSI 70이네요"라고 다시 말하게 하는 것은 토큰·환각만 더하고 새 정보가 없다. *글*로 된 입력이 필요한 곳은 뉴스·공시뿐이라 LLM 분석가는 뉴스 1명만 남긴다.
- **결정 에이전트가 "조건부"인 이유**: 뉴스 판단을 숫자(촉매 강도 0~1)로 내면 코드가 그 숫자를 점수에 섞어 규칙으로 결정할 수도 있다. 결정 에이전트의 고유 가치는 *촉매의 성격까지 본 질적 판단*(예: "한 번뿐인 소송 승소라 지속성 없음")과 *포트폴리오 차원 종합*인데, 그것이 비용을 떼고도 코드 규칙을 이기는지는 *증명 대상*이다.
- **결정 에이전트 — 보정통계 주입**: 입력에 출처별(뉴스·결정자)·레짐별 "과거 확신도 vs 실제 적중률"을 함께 넣어 정량 판단하게 한다. 소표본일 땐 수축이 자동으로 중립 쪽으로 끌어당겨 영향을 줄이므로, 데이터가 적다고 이 로직을 끄지 않는다.
- **결정 에이전트 — 보유 포지션 논지 재평가**: 매 사이클 보유 종목별로 "진입 논지가 여전히 유효한가 / 청산·증축·트레일링"을 신규 진입과 **동등한 1급 판단**으로 다룬다.
- **섹터·테마 상대강도 반영**: 섹터 상대강도는 *코드가 숫자로 계산*해 결정 에이전트 입력에 직접 넣는다. 한국장은 테마 순환이 지배적이라 주도 섹터의 종목은 같은 셋업도 잘 간다.
- **진입 논지 구조 의무화**: 매수 제안마다 왜 지금 사는가(촉매)·틀렸다고 인정할 가격(무효화선)·R:R·수수료 빼고 남는 엣지를 반드시 적게 한다. 검증 가능한 가설·무효화선을 미리 못박아야 규율이 서고 사후 학습 귀속이 깨끗해진다. 미충족·엣지 부족이면 무거래.
- **이벤트 캘린더는 코드 플래그로 처리**: 실적일·옵션만기·FOMC·금통위·지수 리밸런싱·락업 해제 같은 달력 사실은 추론이 불필요하므로 코드가 플래그로 산출해 결정 에이전트에 직접 주입한다.
- **공시 본문은 별도 분석가가 아니라 뉴스·촉매 에이전트의 입력 확장**: 공시 *본문*은 새 전문가 에이전트가 아니라 *위 뉴스·촉매 분석가가 함께 읽는 글 입력*이다. 다만 장문이라 유형 필터·섹션 추출·요약 같은 압축 전처리가 필요. 
- **비용·복잡도 — 사이클당 LLM 호출 0-2회**: 뉴스 1 + 결정 0-1 + 회고 0-1. 정기 2회 + 이벤트 트리거 기준 **월 약 2만원**.

## 3-3. 리포 구조

**구조를 떠받치는 4개 불변식**:

- **모드 분기는** `config/`**·**`broker/kis_client.py`**에서만** 정의.
- **SQLite는 유일한 프로세스 공유점** — 매매 코어·회고·대시보드는 `memory/db.py`의 `connect()`*만* 거쳐 같은 파일에 닿는다. 직접 `sqlite3.connect()` 금지(`ruff` 강제). 
- **LLM은 두 칸에서만** — `agents/`만 Anthropic SDK를 호출.
