## 10. 운영
> 매매 로직이 옳아도 운영이 무너지면 사고가 난다. 이 장은 "시스템을 안 죽고, 두 번 주문 안 가게, 조용히 실패하지 않게 돌리는 법"의 단일 소스다.
>
> 1인 무인 운영의 실패는 거의 항상 전략의 문제가 아니라 운영의 문제다 — 조용한 실패, 키 만료, 디스크 풀, 시계 어긋남, 부분 체결 미정리. 아래 각 절은 그 전형적 실패 하나와 그것을 막는 규칙을 짝지어 놓은 것이다.

### 10.1 사이클 idempotency — 도중에 죽어도 두 번 주문 안 가게
**실패 시나리오** : 5단계(주문 실행)에서 KIS 체결까지 됐는데 6단계(기록) 직전에 프로세스가 죽으면, DB엔 주문이 없고 KIS 잔고엔 체결이 있다. 다음 사이클의 잔고 정합성 게이트가 불일치를 잡아 정지시키고, 사람이 손으로 맞추기 전까지 사이클이 안 돈다 — 그 사이 손절·진입 기회가 사라진다.

원칙
— 주문 송출 효과의 정확히 한 번 보장
- 사이클 시작 시 `Cycles`에 `intent` 상태로 한 줄 적재(주문 시도 전). 이로써 무엇을 하려 했는지가 먼저 디스크에 남는다.
- `Cycles.Status`는 `intent` → `scoring` → `deciding` → `ordering` → `recorded`의 상태 머신이고, 중단은 `failed`, 건너뜀은 `skipped`다.
- 모든 주문은 `Orders.ClientOrderId` = `{CycleId}-{SymbolId}-{Side}-{Seq}`를 기본키로 갖는다. 같은 의도면 항상 같은 값이 나오므로, 재시작 후 같은 주문을 다시 만들려 해도 삽입 단계에서 거부된다. 이게 중복 주문 방지의 실체다.
- 재진입 복구: 사이클 진입점이 가장 먼저 복구 루틴을 호출한다. `intent`·`ordering`으로 남은 직전 사이클을 찾아, 그 주문 의도와 KIS 실체결(주식일별주문체결조회 `VTTC0081R`/`TTTC0081R`, 모의 지원)을 대조해 재동기화한 뒤 정상 사이클을 시작한다.
- 리스크 검증의 선행 게이트(잔고 정합성)는 이 복구 이후에 돌기 때문에, 정상 복구된 뒤에는 안전 정지가 뜨지 않는다.


### 10.2 KIS 운영 정책 — 토큰·호출 한도·5xx
KIS의 운영 현실: 접근토큰 24시간 만료(발급은 1분 1회), 초당 호출 한도(실전·모의가 다름), 모의계좌 분기 갱신, 일시적 5xx 점검창. 이를 결정론 정책으로 흡수한다.

- **토큰 자동 갱신**: 만료 5분 전에 자동 재발급. 실패 시 지수 백오프(1→2→4초) 3회, 모두 실패하면 안전 정지. 발급한 토큰은 파일에 캐싱해 1분 1회 제한을 피한다.
- **호출 한도**: 모든 KIS 호출을 토큰 버킷에 통과시켜 초당 한도의 80%까지만 쓴다. 한도는 `config/rate_limits.toml`에 모드별로 두고 코드에 박지 않는다.
- **5xx 처리**: 일시적(503·504)은 지수 백오프 3회. 영구적(401·403·404)은 즉시 안전 정지.
- **주문 송출은 재시도 금지** — 중복 주문 위험이 손실보다 크다. 단 송출 실패는 접수됐는지 모르는 상태이므로, 재시도 대신 **그 사이클 안에서 즉시 1회 체결조회**로 접수 여부를 확인한다(조회는 중복 위험이 없다). 접수됐으면 `Orders`·`Positions`를 동기화하고 **그 매수에 손절 스톱이 걸렸는지까지 확인**해 미등록이면 즉시 등록한다(5.1 "손절 예약 확인 후 매수 완료 처리"). 이렇게 해서 다음 사이클까지 손절 없는 포지션이 방치되는 구멍을 사이클 안에서 닫는다.
- **모의계좌 만료 알림**: 만료일을 적재해 D-30·D-7·D-1에 경고를 보낸다.


### 10.3 일일 배치 실패 — 낡은 데이터로 판단하지 않게
**실패 시나리오**: 장 시작 전 배치(3-1)가 절반만 돌고 죽으면, 그날 사이클은 어제 데이터나 일부만 갱신된 데이터로 점수를 매긴다. 배치 실패는 사이클 실패와 달리 아무 에러 없이 조용히 지나간다.

**원칙**
- 배치는 대상 표를 채울 때마다 `IngestRuns`에 한 줄씩 남긴다 — 대상 건수·성공 건수·적재 행 수·종료 시각·상태(`ok`/`partial`/`failed`).
- 매 사이클 4단계의 **데이터 신선도 검사**가 이 표를 읽어, 오늘 배치가 `ok`가 아니거나 종료 시각이 너무 오래됐으면 그 사이클을 진행하지 않는다.
- `partial`이면 성공 건수를 이어받기 기준으로 삼아 실패한 종목만 재시도한다. 전체를 다시 받지 않는다.
- 배치 실패는 알림 채널로 보낸다. 조용히 지나가면 그날 하루 전체 판단이 낡은 데이터 위에서 이뤄진다.


### 10.4 Heartbeat — 조용한 실패 차단
**실패 시나리오**: cron이 안 돌았거나 토큰 발급 실패로 사이클이 30초 만에 죽으면, DB엔 아무 기록도 없는 상태가 된다. 정기 사이클이라 시각이 지났는데 기록이 없다는 사실 자체가 신호인데, 외부에서 감시하지 않으면 며칠 뒤 대시보드를 열고서야 알게 된다.

**원칙 — 외부 모니터링에 "살아 있다" 신호 보내기**
- 사이클 정상 종료 시 외부 모니터링 서비스(healthchecks.io 등)로 HTTPS ping을 보낸다. 모니터링 측이 예상 시각 + 여유 15분 안에 ping을 못 받으면 알람을 울린다.
- 정상 종료 ping과 안전 정지 ping은 다른 주소를 쓴다. 정지는 즉시 알람, 정상은 안 왔을 때만 알람.
- **알림은 Discord 웹훅**으로 보낸다. 폰·데스크톱·웹에서 같은 알림을 받으므로 기기 하나를 잃어도 확인할 수 있다.
- 같은 채널로 보내는 조기 경보: 일일 배치 실패, 모의계좌 만료 임박, KIS 호출 한도 90% 도달, 디스크 80% 사용, **메모리 스왑 사용 발생·DB 연결 실패**(10.13), 백업 실패, 시계 동기화 오차, 데이터 출처 폴백 발생, **외부 현금흐름 감지**(10.18 — 차단이 아니라 "기록했고 그대로 진행했다"는 통지다).


### 10.5 시크릿 관리
**실패 시나리오**: KIS App Key/Secret이 평문으로 떨어지면 도난 1회로 자본 전체가 위험해진다. 실수로 커밋하거나 스크린샷에 찍히는 사고도 같다.

- 시크릿은 **서버 로컬** `.env`(`chmod 600` + 디스크 암호화)에만 둔다. 클라우드 시크릿 매니저는 우리 규모엔 과잉이다.
- `.gitignore`로 리포 유출을 강제 차단하고, `pydantic-settings`가 환경변수에서만 읽는다.
- **DB·로그에 시크릿이 들어가는 경로를 차단**한다. 계좌번호도 마스킹해 저장(`810XXXXX`).
- KIS 키는 6개월마다 회전, 나머지는 노출 의심 시 즉시 회전. 회전 일정은 분기 점검 항목이다.


### 10.6 백업·복구

**실패 시나리오**: 몇 년치 거래 기록(자본곡선·체결·성과 일체)이 서버 디스크 하나에 의존한다. 디스크 사망·랜섬웨어·실수 삭제 시 기록이 영구 손실된다.

- **거래 기록 백업(매 사이클)**: 사이클 종료 후 `Decisions`·`Orders`·`CashFlows`·`Positions`·`Outcomes`만 덤프한다. 행 수가 적어 1초면 끝나고, 다시 만들 수 없는 유일한 데이터가 이것이다. `CashFlows`가 여기 드는 이유는 증권사가 입출금 내역 API를 안 주기 때문이다 — 이 표를 잃으면 어느 돈이 수익이고 어느 돈이 내가 넣은 것인지 되짚을 방법이 없다.
- **전체 백업(하루 1회)**: 장 마감 후 `pg_dump`로 DB 전체를 압축 스냅샷 1개로 뽑는다. 백업 중에도 매매·대시보드가 돈다.
- **시장 데이터는 백업 대상이 아니다.** 일봉·수급·종목마스터는 언제든 다시 받을 수 있으므로 백업 용량만 키운다. 날아가면 배치를 다시 돌린다.
- **3-2-1**: 원본(NCP 서버) + 로컬 2차(맥 또는 외장 디스크) + 클라우드(업로드 전 암호화). 세 사본이 서로 다른 장애에 독립적이어야 한다.
- **암호화**: 서버 디스크 암호화를 기본으로 하고, 서버 밖으로 나가는 덤프 파일은 보내기 전에 암호화한다.
- **복구 리허설**: 분기마다 백업에서 복원해 사이클 1회 정상 동작을 확인한다. 목표는 데이터 손실 1일·복구 4시간 이내.
- **세무 자료 export**: 매년 1회 `Orders`·`Outcomes`·`CashFlows` 전체를 CSV로 뽑아 원본과 독립적으로 보관한다. DB가 날아가도 신고 자료는 살아남아야 한다.


### 10.7 시간대 정규화
**실패 시나리오**: KRX는 KST, yfinance는 UTC/ET, KIS 응답 형식은 항목마다 다르다. 시간대 정보 없는 시각이 한 번이라도 섞이면 9시간 차이로 사이클이 안 도는 시각에 돌거나 도는 시각에 안 돈다.

- **내부 표준은 UTC + 시간대 인식**(`datetime.now(UTC)`). 사람에게 보여줄 때만 KST로 바꾼다.
- **경계 함수 한 쌍**(`core/timeutils.py`)만이 KIS↔내부 변환을 담당한다. 다른 코드는 직접 변환하지 않는다.
- 외부 응답이 시간대 없이 들어오면 명시적으로 거부한다.
- 거래일·휴장·반장 판정은 `exchange_calendars`에 위임하고, KIS 영업일 API로 2중 점검한다(라이브러리가 임시휴장을 늦게 반영할 수 있다).
- **CI 룰**: 인자 없는 `datetime.now()` 호출을 코드 전체에서 금지한다.


### 10.8 시계 동기화
손절 트리거·데이터 컷오프·heartbeat가 모두 시계에 의존한다. 시계가 1분 어긋나면 종가 컷오프를 오판해 잘못된 데이터로 결정한다.

- OS의 NTP 자동 동기화를 켠다(`timedatectl set-ntp true`).
- 사이클 시작 시 동기화 상태를 점검하고, 오차 ±5초를 넘으면 경고를 보낸 뒤 동기화 후 재시작한다.


### 10.9 "if 실전 then" 분기 금지의 강제
**실패 시나리오**: "모의/실전은 설정값 하나로 전환, 코드에 모드 분기 없음"을 원칙으로만 적어두면 1년 뒤 누군가(=본인)가 슬쩍 분기를 박는다. 한 번 박히면 모의에서 검증한 코드와 실전에서 도는 코드가 조용히 갈라진다.

- CI 체크로 `if .*(live|paper|backtest).*:` 패턴을 차단한다. 예외 허용은 `config/`·`broker/kis_client.py`·테스트·문서뿐이다.
- 모드 차이는 **설정값**(KIS 도메인·계좌번호·호출 한도·주문 구분)으로만 흡수한다 — 코드는 모드를 모른다.
- **동일성 매트릭스**: 핵심 모듈을 모의·실전 두 모드에서 같은 골든 케이스로 돌려 결과가 같은지 검증한다. 다르면 어딘가에 분기가 숨어 있다는 신호다.


### 10.10 로그 회전
- 구조화(JSON) 로그를 일별 회전. 최근 30일 원본, 31~365일 압축, 이후 삭제.
- 1차 자료는 DB에 따로 있으므로 로그는 디버깅용으로만 본다.
- 디스크 80% 사용 시 알림.


### 10.11 스키마 변경
**실패 시나리오**: 컬럼 추가를 손으로 하다가 몇 년치 거래 기록이 깨진다.

- 스키마 변경은 **Alembic**으로만 한다. 순번이 붙은 변경 파일이 쌓이고, 어느 버전까지 적용됐는지를 DB가 스스로 기록한다.
- **forward + backward를 둘 다** 작성해 되돌릴 수 있게 한다.
- Alembic은 **스키마 변경 관리에만 쓴다.** 조회·적재 쿼리는 지금처럼 직접 쓴 SQL 그대로다(ORM을 두지 않는다).
- 마이그레이션 실행 전에 자동 백업, 실행 후에 정합성 체크(참조 무결성·필수 컬럼 채움)를 돌린다.


### 10.12 배포
**호스트**: **NCP 서울 Micro 서버 1대**(vCPU 1개·메모리 1GB). 선검증에서 KIS가 해외 IP를 차단함을 확인했기 때문에 **한국 IP 상시 호스트가 전제**이고, 그 조건에서 가장 싼 선택지가 이것이다. 서버 요금은 무료 기간 동안 0원이고 공인 IP만 월 4천 원대다. 더 먼 목표는 자택 맥미니(비용 0·완전 자가소유·가정용 IP)이며, 설계가 호스트 비의존이라 전환 비용은 작다.

**무엇이 어디서 도는가**

| 위치         | 도는 것                                         | 비용      |
| ---------- | -------------------------------------------- | ------- |
| **NCP 서버** | 일일 배치 · 매매 사이클(cron) · PostgreSQL · 대시보드 API | 월 4천 원대 |
| **Vercel** | 대시보드 화면(정적 파일)                               | 0원      |
| **개발용 맥**  | 백테스트 · 파라미터 튜닝 · 개발                          | 0원      |

**백테스트는 서버에서 돌리지 않는다.** 몇 년치 전 종목 재생은 무겁고 매일 돌 이유도 없으며, 입력이 parquet 캐시라 서버 DB가 필요 없다. 서버는 매일 도는 것만 맡는다. 이 분리가 메모리 1GB를 지키는 가장 큰 수단이다.

**메모리 1GB 예산** — 상시 점유와 배치 피크가 겹쳐도 여유가 남아야 한다.

| 항목                | 목표     |
| ----------------- | ------ |
| OS                | ~120MB |
| PostgreSQL        | ~150MB |
| 대시보드 API(uvicorn) | ~120MB |
| 일일 배치 피크          | ~400MB |
| **최대 동시 점유**      | ~790MB |

- **일일 배치는 종목을 나눠 처리한다.** 2,500종목을 한 번에 메모리에 올리면 피크가 배로 뛴다. 청크 경계는 `IngestRuns`의 이어받기 단위와 일치시킨다(10.4).
- **배치의 최대 메모리 사용량을** `IngestRuns`**에 기록한다.** 1GB에 들어가는지는 계산이 아니라 실측으로 판단한다. Micro 서버는 **스펙을 나중에 못 올리므로**, 여유가 줄어드는 추세가 보이면 서버 이전을 미리 계획해야 한다.
- 스왑 2GB는 안전망이지 상용 경로가 아니다. 스왑 사용량이 0을 벗어나면 경보를 보낸다.

**프론트 배포**: 대시보드 화면은 **Vercel**에 올린다. 저장소에 push하면 자동으로 빌드·배포된다. 정적 파일만 올라가므로 **실거래 수치는 Vercel에 저장되지 않는다**.

**프론트와 서버를 잇는 길**: Vercel 화면은 `https`로 열리는데 서버에는 도메인이 없어 자물쇠(HTTPS)를 직접 달 수 없다. **Tailscale Funnel**이 서버에 고정 주소(`https://…ts.net`)와 인증서를 무료로 붙여준다. Vercel은 `/api/`* 요청을 그 주소로 넘긴다.

```
브라우저 ──https──▶ Vercel(화면) ──https──▶ Tailscale Funnel ──▶ NCP 서버
```

- **전 구간이 암호화**되고, 도메인 비용이 0이다.
- 터널이 바깥으로 연결을 여는 방식이라 **서버 방화벽에 인바운드 포트를 하나도 열지 않는다.** 공인 IP를 훑는 스캐너에 노출될 표면이 없다.
- 브라우저 입장에서는 화면과 API가 같은 주소이므로 로그인 쿠키를 안전하게 다룰 수 있다(8.6).
- `uvicorn`은 `127.0.0.1`에만 바인딩한다. 터널 말고는 닿을 경로가 없다.

**배포 규칙**
- 배포 윈도우는 사이클 사이(11:00~13:00) 또는 장 마감 후(16:00 이후). 사이클이 도는 시각에는 배포하지 않는다.
- 배포 전 `Cycles`에 `intent`·`ordering` 상태 행이 있는지 확인한다. 있으면 완료를 기다리거나 정지시킨 뒤 배포한다.
- 스키마 변경이 포함된 배포는 자동 백업·정합성 체크를 통과한 뒤에만 진행한다.
- 롤백은 직전 git tag로 복귀 + 마이그레이션 backward 실행. 롤백 후에도 사이클 복구 루틴이 정상 동작해야 한다.
- **프론트와 백엔드는 따로 배포한다.** 화면만 고칠 때는 서버를 건드리지 않으므로 매매가 멈추지 않는다. 다만 API 응답 형태를 바꾸는 배포는 백엔드를 먼저 올린다.


### 10.13 부분 체결과 주문 유형

**부분 체결이란**: 100주를 주문했는데 그 순간 그 가격에 팔겠다는 물량이 60주뿐이면 60주만 체결되는 것이다. 잔량을 어떻게 할지 지정하지 않으면 KIS가 대기 주문으로 남겨 시차를 두고 나눠 체결할 수 있고, 그러면 *얼마를 샀는지(사이징)*와 *언제 다 팔렸는지(청산)*의 정밀도가 망가진다.

| 용도 | 주문 구분(`ORD_DVSN`) | 이유 |
| - | - | - |
| **진입** | 실전 `11` IOC지정가 / 모의 `00` 일반지정가 | 즉시 체결 가능한 만큼만 진입하고 잔량은 자동 취소. 전량 체결 보장보다 체결 가능량 즉시 진입이 사이즈 정밀도에 유리하다. **모의는 IOC 미지원**이라 `00`으로 보정하되, `if mode` 분기가 아니라 모드별 데이터 룩업으로 처리한다 |
| **청산(강제)** | 실전 `13` IOC시장가 / 모의 `01` 시장가 | 무조건 즉시 청산 의도, 잔량 취소 |
| **손절 예약**  | `22` 스톱지정가 | 발동가 도달 시 KIS가 자동 송출. 우리가 꺼져 있는 18시간 30분(14:30 → 다음날 09:00)을 메우는 장치 |
| **스톱 정정**  | 정정취소 API (`TTTC0013U`) | 트레일링·본전 상향 시 기존 스톱을 정정 |

**처리**
- IOC가 잔량을 자동 취소하므로 보통 발생하지 않지만, 진입이 부분 체결되면 `Orders` 한 행의 `filledQuantity`·`averageFillPrice`를 갱신하고 `Positions`의 평단을 가중평균으로 다시 계산한다.
- 청산에서 잔량이 남으면(스톱이 일부만 체결) 다음 사이클에서 잔여를 시장가로 강제 청산한다.

### 10.15 단계적 도입
- 이 장의 항목을 한꺼번에 구현할 필요는 없지만, 원칙은 착수 시점에 모두 명문화돼 있어야 한다.

### 10.16 외부 노출 금지 (자본시장법)
**실패 시나리오**: 이 시스템은 1인 자기자본 운영이라 합법이다. 그러나 결정·수익률·체결을 외부에 공개하면(블로그·SNS·구독제·"포트폴리오 따라하기") 무인가 투자자문업에 해당해 자본시장법 위반 위험이 생긴다. 시스템 자체보다 운영자의 부주의가 법적 리스크의 주된 경로다.

- **공개 노출 금지**: 결정·수익률·체결을 불특정 다수가 볼 수 있는 곳에 올리지 않는다. 대시보드에 로그인을 두는 이유가 이것이다(8.6) — 인터넷에서 주소가 열려 있어도 **비밀번호를 아는 나만 볼 수 있으면 "공개"가 아니다**.
- **화면과 데이터를 분리한다**: Vercel에 올라가는 것은 빈 화면(정적 파일)뿐이고, 종목·수익률·체결은 로그인한 뒤 서버에서만 내려온다. **실거래 수치가 Vercel이나 저장소에 남는 경로를 만들지 않는다** — 화면 코드에 값을 넣어두는 것, 스크린샷을 커밋하는 것 모두 금지다.
- **검색에 걸리지 않게 한다**: `robots.txt`와 응답 헤더로 색인을 차단한다.
- **회색지대**: 시스템 설계만 공유하는 것은 일반적으로 문제없지만, 실거래 수익률·구체 종목·매매 시점을 공유하면 위반 가능성이 있다. 수치를 가린 설계 추상화까지만 허용한다.
- **저장소**: 코드는 비공개 저장소. 설계 문서는 실거래 수치를 포함하지 않는 한 공개 가능. 데이터·DB 파일·시크릿·로그는 `.gitignore`에 강제 등록한다.
- 이 절은 법률 자문이 아니다. 실제 외부 공개는 전문가 상담 후에만 진행한다.


### 10.17 데이터 출처 백업 경로
**실패 시나리오**: 데이터 소스가 대부분 단일 출처다. yfinance는 비공식 크롤이라 차단·구조 변경 시 며칠씩 끊기고, DART도 단기 장애가 있다. 단일 출처 장애가 곧 사이클 정지로 직결된다.

| 1차 출처                       | 2차 백업        | 결측 시                    |
| --------------------------- | ------------ | ----------------------- |
| **KIS** (시세·수급·종목마스터·계좌·주문) | **없음**       | 그 사이클 무거래(보유 청산 로직만 가동) |
| **yfinance** (지수)           | Stooq        | 벤치마크 비교만 지연(결정 무관)      |
| **DART** (기업행위)             | KIND(거래소 공시) | 다음 배치에서 재시도             |
| **exchange_calendars** (휴장) | KRX 휴장공지     | KIS 영업일 API로 2중 확인      |

**KIS에는 백업이 없다 — 있을 수가 없다.** 시세·수급·계좌·주문이 전부 KIS 하나로 들어오므로, KIS가 죽으면 데이터를 어디서 구해와도 주문을 낼 수 없다. 그래서 KIS 장애는 폴백 문제가 아니라 정지 문제다. (네이버 금융은 백테스트용 과거 데이터를 1회 수집하는 경로일 뿐 운영 폴백이 아니다 — 실시간 시세·잔고·주문을 대신하지 못한다.)

- 출처별 어댑터가 1차 → 2차 순으로 시도하고, **동일한 형태의 데이터를 반환**해 호출 측은 어느 출처를 썼는지 모른다. 대신 사용된 출처 라벨을 `IngestRuns.Source`에 남겨 사후에 어느 날 백업으로 돌았는지 추적한다.
- 폴백이 발생하면 시스템을 멈추지 않고 주의 알림을 보낸다. 다음 실행에서 1차 출처를 자동 재시도한다.
- 폴백 경로가 코드에만 있고 실제로 안 도는 사고를 막기 위해, 분기마다 1차를 일부러 차단해 검증한다.


### 10.18 입출금 운영 규칙
**실패 시나리오**: 시스템은 이체를 "내가 고의로 한 일"로 인식하지 못한다. 시스템 입장에서는 그냥 돈이 증발하거나 추가된 것이다. 아무 규칙 없이 아무 때나 이체하면 사이클이 도는 도중에 자본이 바뀌어, 사이징 분모와 게이트 판정이 서로 다른 자본을 보는 경쟁 상태가 생긴다.

**이체는 시간창을 지킨다 — 장 마감 후(15:30) ~ 다음날 일일 배치 전.**
정기 사이클은 하루 한 번 14:30이므로(03-arch 3-1), 이 창을 지키면 사이클 도중에 자본이 바뀔 일이 원천적으로 없다. 인프라도 코드도 필요 없는 비용 0의 안전장치다.

**출금 전에 안전 출금 가능액을 확인한다.**
대시보드 ① 나의 정보에 뜨는 `예수금 − 미체결 매수 주문 금액`이다. 이 숫자를 넘겨 빼면 미수가 나고, 미수는 즉시 `SafeStop`이다(05-risk 5.1). 폰에서 이 숫자 하나만 보고 이체하면 된다.

**감지는 자동, 라벨은 사후.**
사이클이 잔차를 감지하면 `CashFlows`에 남기고 Discord로 알린 뒤 **매매를 그대로 계속한다.** 라벨은 언제 붙여도 된다 — 며칠 뒤에 붙여도 시스템은 멈추지 않는다.

```bash
python -m ops.cashflow list                                  # 미확인 흐름 보기
python -m ops.cashflow confirm --id F123 --kind deposit      # 입금으로 확정
python -m ops.cashflow reclassify --id F123 --kind dividend  # 배당이었다면 정정
```

Tailscale + SSH로 폰에서도 같은 명령을 친다. 대시보드에 두지 않는 이유는 라벨 붙이기가 쓰기라서, 대시보드에 넣으면 읽기 전용 경계(08-dashboard 8.1)가 깨지기 때문이다.

**입금과 배당을 반드시 구분해서 라벨링한다.** 둘 다 "주식은 그대로인데 현금만 늘어남"으로 똑같이 보이지만, 입금은 원금 추가라 수익률에서 빼야 하고 배당은 수익이라 넣어야 한다. 오분류하면 배당 수익을 통째로 지우거나 입금을 수익으로 잡는다.

**금액 서명(선택).** 이체 금액 끝 세 자리를 약속값으로 맞추면 시스템이 `Kind`를 자동 확정한다 — 입금 `...777`, 출금 `...555`. 예를 들어 200만원을 넣을 때 2,000,777원을 보낸다. `cashflow_signature_enabled=true`로 켜며 **기본은 꺼져 있다.** 인프라 0, 비용 0으로 라벨링 손이 사라진다.

**관찰 모드.** `cashflow_observation_mode`가 켜져 있는 동안은 흡수 임계 미만의 잔차까지 전부 기록하되 Discord는 자본 1% 이상에서만 울린다. 몇 주 쌓인 잔차 분포를 보고 흡수 임계(현재 `max(1,000원, 자본의 0.01%)`)를 실측으로 확정한 뒤 끈다. 잔차가 계속 한 방향으로만 쌓이면 그건 오차가 아니라 계산식 버그 신호다.
