# 11. 인프라 — 이 시스템이 실제로 어디서 어떻게 도는가

01~10장은 *무엇을 만들 것인가*(설계)를 다룬다. 이 장은 그 설계가 **실제 기계 위에서
어떻게 놓여 있는가**를 다룬다. 서버·데이터베이스·배포를 처음 접한다는 전제로 쓴다.

> 서버 접속 주소와 열쇠는 이 문서에 적지 않는다. 저장소가 공개돼 있어서, 주소를 적으면
> 그대로 공격 표적이 된다. 접속 정보는 개발용 맥의 SSH 설정과 `.env`에만 둔다.


## 11.1 먼저 큰 그림

이 시스템은 컴퓨터 **세 대**에 나뉘어 있다. 한 대에 다 넣지 않은 이유가 각각 있다.

```
   ┌─────────────────┐         ┌──────────────────────────────────┐
   │  ① 개발용 맥     │         │  ② NCP 서버 (한국, 24시간 켜짐)   │
   │                 │         │                                  │
   │  코드 작성       │  코드   │   매매 프로그램  ←→  PostgreSQL   │
   │  백테스트        │ ──────▶ │        ↑              (저장소)    │
   │  git push       │         │        │                  ↑       │
   └─────────────────┘         │   시계(cron)         조회 API     │
            │                  └──────────────────────────────────┘
            │ git push                          ↑
            ▼                                   │ 암호화된 길
   ┌─────────────────┐                          │ (Tailscale Funnel)
   │  ③ Vercel       │                          │
   │  대시보드 화면   │ ─────────────────────────┘
   └─────────────────┘
            ▲
            │ 브라우저로 접속 (비밀번호 로그인)
          [ 나 ]
```

한 문장으로 요약하면 이렇다. **개발용 맥에서 코드를 쓰고, git으로 밀어 올리면, NCP 서버와
Vercel이 각자 그 코드를 받아 간다. 서버는 매일 정해진 시각에 매매 프로그램을 돌려 결과를
데이터베이스에 남기고, 나는 Vercel에 있는 화면으로 그 결과를 본다.**


## 11.2 왜 컴퓨터가 세 대인가

**개발용 맥으로는 안 되는가?** 안 된다. 매매는 매일 정해진 시각에 자동으로 돌아야 하는데,
맥은 내가 닫으면 꺼지고 들고 다니면 인터넷이 끊긴다. 14:30에 노트북이 가방 안에 있으면
그날 매매는 없다. **항상 켜져 있고 항상 같은 자리에 있는 컴퓨터**가 필요하다.

**그러면 서버 한 대에 다 넣으면?** 매매·데이터베이스·조회 API까지는 한 대에 있다. 다만
**화면만 따로** 뺐다. 이유는 두 가지다.

- 서버가 작다. 메모리 1GB짜리라 화면까지 얹으면 빠듯하다.
- 화면은 자주 고치는데, 화면을 고칠 때마다 매매 프로그램이 도는 서버를 건드리면 매매가
  멈출 위험이 생긴다. 따로 두면 화면만 백 번 고쳐도 매매는 한 번도 안 멈춘다.

**백테스트는 왜 맥에서 하는가?** 몇 년치 전 종목을 재생하는 계산이라 무겁고, 매일 할 일도
아니다. 작은 서버에 그 부담을 지우면 정작 매일 해야 할 매매가 밀린다.


## 11.3 서버 — NCP에서 빌린 컴퓨터

**서버란 그냥 남의 건물에 있는 컴퓨터다.** 24시간 켜져 있고, 인터넷에 연결돼 있고, 화면과
키보드 대신 원격으로 명령을 넣어 쓴다. 네이버 클라우드(NCP)에서 월 4천 원대에 빌렸다.

- 운영체제: Ubuntu 24.04 (리눅스). 화면 없이 글자로만 조작한다.
- 성능: CPU 1개, 메모리 1GB, 디스크 10GB. 작다. 그래서 백테스트를 여기서 안 돌린다.
- 시간대: 한국 시간(KST)으로 맞춰져 있고, 인터넷 시계와 자동 동기화된다. 매매 시각이
  1분만 틀려도 곤란하기 때문이다.

**왜 한국에 있는 서버여야 하는가?** 한국투자증권 API가 해외에서 오는 접속을 막는다.
미국이나 일본 서버를 쓰면 아무리 열쇠가 맞아도 거부당한다.

### 원격 접속(SSH)

서버에 명령을 넣으려면 **SSH**라는 방식으로 접속한다. 화상통화 없이 글자만 오가는 원격
조종이라고 보면 된다. 비밀번호 대신 **열쇠 파일**(`.pem`)로 신원을 증명한다. 비밀번호는
추측당할 수 있지만 열쇠 파일은 사실상 불가능하기 때문이다.

```bash
ssh -i ~/.ssh/열쇠파일.pem root@<서버주소>
```

접속하면 서버 안에서 명령을 치는 상태가 된다. `exit`로 빠져나온다.

> **알아둘 것**: 서버의 22번 문(SSH 포트)이 인터넷에 열려 있어서, 전 세계 자동 프로그램이
> 하루 종일 비밀번호를 찍어보고 있다. 열쇠 파일 방식이라 뚫리지는 않지만, 나중에
> Tailscale로만 접속하도록 막는 것이 안전하다.


## 11.4 저장소 — PostgreSQL

**데이터베이스는 표(엑셀 시트)를 여러 장 담아두고, 필요한 줄만 빠르게 꺼내 주는
프로그램이다.** 이 시스템은 PostgreSQL을 쓰고, 서버 안에서 돈다.

표는 19장이 있다. 몇 개만 예를 들면:

| 표 | 담는 것 |
|---|---|
| `daily_bars` | 종목별 일봉(시가·고가·저가·종가·거래량) |
| `daily_scores` | 매일 계산한 종목 점수 |
| `cycles` | 매매 사이클이 언제 돌았고 어떻게 끝났는지 |
| `decisions` | 어떤 종목을 왜 사기로/팔기로 했는지 |
| `orders` | 실제로 낸 주문과 체결 결과 |
| `positions` | 현재 보유 종목 |
| `outcomes` | 청산이 끝난 거래의 손익 |
| `cash_flows` | 입출금 기록 |
| `watch_runs` | 장중 감시가 언제 돌았고 무엇을 했는지 |

**왜 파일이 아니라 데이터베이스인가?** 매매 프로그램이 쓰는 동시에 대시보드가 읽어야
하는데, 파일이면 그 순간 충돌한다. 데이터베이스는 이걸 안전하게 처리해 준다.

### 계정을 둘로 나눈 이유

같은 데이터베이스에 접속 계정이 **두 개** 있다.

| 계정 | 할 수 있는 것 |
|---|---|
| `alphaloop_core` | 읽기 + 쓰기 — 매매 프로그램이 쓴다 |
| `alphaloop_dashboard` | **읽기만** — 대시보드가 쓴다 |

대시보드는 보여주기만 하면 되니까 쓰기 권한이 필요 없다. 권한을 주지 않으면, 대시보드
코드에 실수나 허점이 있어도 **거래 기록을 망가뜨릴 방법 자체가 없다.** 문을 잠그는 게
아니라 애초에 문을 만들지 않는 방식이다.

두 계정의 비밀번호는 서버의 `.env` 파일 안에만 있다. 이 파일은 서버 주인만 읽을 수 있게
권한이 걸려 있고(`600`), git에도 올라가지 않는다.

### 데이터베이스는 바깥에서 못 닿는다

PostgreSQL은 `127.0.0.1`이라는 주소에만 귀를 열고 있다. 이건 **"내 컴퓨터 자신"** 을
뜻하는 특별한 주소다. 즉 서버 안에서 도는 프로그램만 접속할 수 있고, 인터넷에서는
아무리 두드려도 닿지 않는다.


## 11.5 백엔드 — 데이터를 꺼내 주는 프로그램

대시보드 화면이 "내 잔고 얼마야?"라고 물으면, 누군가 데이터베이스에서 꺼내 답해 줘야
한다. 그 역할이 **백엔드 API**다. 이 프로젝트에서는 `dashboard/api.py`가 그것이다.

**API란 "정해진 질문에만 정해진 형식으로 답하는 창구"다.** 예를 들어:

| 질문(주소) | 답 |
|---|---|
| `GET /api/account` | 예수금·총자산·보유 종목 |
| `GET /api/trades` | 거래 목록 |
| `GET /api/equity-curve` | 자본이 어떻게 변해왔는지 |
| `GET /api/alerts` | 경고·정지 이력 |

**FastAPI**는 이런 창구를 쉽게 만들게 해 주는 파이썬 도구고, **uvicorn**은 그 창구를
실제로 열어두고 손님을 받는 프로그램이다. FastAPI가 "무엇을 답할지"를 정하고, uvicorn이
"문을 열고 서 있는" 역할이다.

이 API도 `127.0.0.1:8000`에만 귀를 연다. 즉 **인터넷에서 직접 닿을 수 없다.**
바깥에서 오는 길은 11.7의 Funnel 하나뿐이다.

### 꺼져도 알아서 다시 켜진다

서버를 재부팅하거나 프로그램이 죽으면 API도 멈춘다. 그래서 **systemd**라는 리눅스의
관리자에게 맡겨 뒀다. systemd는 "이 프로그램을 항상 켜 두고, 죽으면 5초 뒤 다시 켜라"는
지시를 지킨다. 그 지시서가 `ops/deploy/alphaloop-api.service` 파일이다.

```bash
systemctl status alphaloop-api    # 지금 잘 돌고 있나
systemctl restart alphaloop-api   # 다시 켜기
```


## 11.6 프론트엔드 — 눈에 보이는 화면

**프론트엔드는 브라우저에 그려지는 화면이다.** 이 프로젝트에서는 React라는 도구로 만들었고
(`dashboard/web/`), 완성하면 HTML·CSS·JavaScript 파일 몇 개로 압축된다.

중요한 건 **이 파일들 안에 거래 데이터가 하나도 없다**는 점이다. 화면은 빈 틀이고, 열릴
때마다 백엔드에 물어서 숫자를 채운다. 그래서 화면 파일이 공개된 곳에 있어도 내 수익률이
새지 않는다. `docs/10-operations.md` 10.16이 요구하는 분리가 이것이다.

### Vercel

**Vercel은 이런 화면 파일을 인터넷에 올려 주는 무료 서비스다.** GitHub 저장소와 연결해
두면, 코드를 밀어 올릴 때마다 알아서 새 화면을 만들어 배포한다. 내가 할 일이 없다.

- 주소: `alphaloop-web.vercel.app`
- 배포 시점: `git push` 할 때마다 자동
- 비용: 0원


## 11.7 셋을 잇는 길 — Tailscale Funnel

여기가 가장 헷갈리는 부분이라 천천히 본다.

**문제**: 브라우저는 Vercel에서 화면을 받는다. 그런데 데이터는 NCP 서버에 있다. 서버에는
`example.com` 같은 도메인이 없어서 `https://` 주소를 만들 수가 없다. 요즘 브라우저는
`https`가 아닌 곳으로 요청을 보내려 하면 막는다. 도메인을 사면 되지만 돈이 든다.

**해결**: **Tailscale Funnel**이 서버에 공짜로 `https` 주소를 붙여 준다.

```
https://alphaloop-ncp.<...>.ts.net  →  서버 안의 127.0.0.1:8000
```

Funnel이 좋은 이유가 하나 더 있다. 보통 바깥에서 서버로 들어오려면 **서버 방화벽에 문을
뚫어야** 하는데, Funnel은 반대로 **서버가 바깥으로 연결을 거는** 방식이다. 그래서 문을
하나도 안 뚫는다. 인터넷을 훑고 다니는 자동 공격 프로그램에게 보일 표면이 없다.

### 그런데 왜 브라우저에는 한 주소로 보이는가

Vercel에 `vercel.json`이라는 설정이 있고, 거기 이렇게 적혀 있다.

```json
"rewrites": [
  { "source": "/api/:path*", "destination": "https://alphaloop-ncp.<...>.ts.net/api/:path*" }
]
```

이건 **"`/api/`로 시작하는 요청이 오면 Vercel이 대신 받아서 서버로 넘겨라"** 는 뜻이다.
그래서 브라우저 입장에서는 화면도 데이터도 전부 `alphaloop-web.vercel.app`에서 오는
것처럼 보인다. 이게 중요한 이유는 다음 절에서 나온다.

전체 경로를 그리면 이렇다.

```
브라우저 ──https──▶ Vercel ──https──▶ Tailscale Funnel ──▶ 서버의 API ──▶ PostgreSQL
```

전 구간이 암호화돼 있고, 도메인 비용은 0원이다.

> **주의**: Funnel은 한 번에 한 곳만 가리킨다. 화면 개발용 가짜 데이터 서버
> (`dashboard/devserve.py`, 8787 포트)를 가리키게 두면, 가짜 데이터가 인터넷으로 나간다.
> 지금은 운영 API(8000)를 가리키고 있다. `tailscale funnel status`로 확인할 수 있다.


## 11.8 로그인 — 비밀번호와 출입증

대시보드에는 내 거래 내역이 다 보인다. 주소만 알면 누구나 볼 수 있으면 안 된다.
`docs/10-operations.md` 10.16이 설명하듯, 법적으로도 문제가 된다.

### 비밀번호는 저장되지 않는다

서버에는 내 비밀번호가 **없다.** 대신 **해시**라는 것이 저장돼 있다.

해시는 비밀번호를 뒤섞어 만든 긴 글자열인데, 두 가지 성질이 있다.
- 같은 비밀번호를 넣으면 항상 같은 결과가 나온다 → 맞는지 확인할 수 있다
- 결과에서 원래 비밀번호를 되돌릴 수 없다 → 서버가 털려도 비밀번호는 안 샌다

이 프로젝트는 `scrypt`라는 방식을 쓴다. 일부러 계산을 느리게(수십 밀리초) 만들어서,
자동 프로그램이 비밀번호를 초당 수백만 번 찍어보는 걸 막는다.

거기에 더해, **연속 5번 틀리면 그 주소를 15분간 막는다.**

### 출입증(토큰)

한 번 로그인하면 그때마다 비밀번호를 다시 칠 수는 없다. 그래서 서버가 **출입증**을 하나
발급한다. 이걸 토큰이라고 부르고, 여기서는 JWT라는 형식을 쓴다.

- **12시간 뒤 만료된다.** 그 뒤엔 다시 로그인해야 한다.
- **브라우저를 닫으면 사라진다.**
- **화면 코드가 읽을 수 없는 쿠키**에 담긴다(`HttpOnly`). 화면 쪽에 문제가 생겨도 출입증이
  함께 새 나가지 않는다.

11.7에서 "브라우저에는 한 주소로 보인다"고 한 게 여기서 효과를 낸다. 화면과 데이터가 같은
주소로 보이니까, 출입증 쿠키가 자연스럽게 실려 간다. 주소가 달랐다면 브라우저가 쿠키를
막았을 테고, 훨씬 까다로운 설정이 필요했을 것이다.

**`/api/health`(살아 있는지 확인)를 빼면 모든 창구에 출입증 검사가 걸려 있다.** 출입증이
없으면 잔고도, 거래 내역도, 아무것도 안 나온다.


## 11.9 cron — 시계가 코드를 부른다

**cron은 리눅스에 원래 들어 있는 알람시계다.** "매주 평일 14시 30분에 이 명령을 실행하라"
같은 지시를 적어두면 그대로 지킨다. 서버가 켜져 있는 한 내가 잠들어 있어도 돈다.

지시서는 `/etc/cron.d/alphaloop` 파일이고, 원본은 저장소의
`ops/deploy/alphaloop.cron`에 있다.

```
0  8      * * 1-5  run_daily_ingest.py    장 시작 전 데이터 준비
30 14     * * 1-5  run_cycle.py           매매 판단 (하루 1회)
0,30 9-13 * * 1-5  run_watch.py           장중 손절 점검 (30분마다)
0,25 14   * * 1-5  run_watch.py            〃  14:25는 사이클 직전 정리
0,25 15   * * 1-5  run_watch.py            〃  15:30은 이미 장 밖이라 15:25
35 15     * * 1-5  run_watch.py --force   마감 정리 (동시호가 체결 반영)
0  16     * * 1-5  ops.backup full        백업
```

감시가 30분 격자에서 두 번 어긋나는 이유는 `docs/10-operations.md` 10.13에 적어 두었다.
요약하면 **14:25는 사이클과 겹치지 않으려고**, **15:25·15:35는 장 마감 직전·직후를
놓치지 않으려고** 그렇게 둔 것이다.

앞의 숫자를 읽는 법: `분 시 일 월 요일`. `30 14 * * 1-5`는 "매월 매일 중 월~금요일의
14시 30분"이라는 뜻이다.

**공휴일은 어떻게 아는가?** cron은 모른다. 대신 각 프로그램이 시작할 때 스스로
"오늘 장이 열리나?"를 확인하고, 휴장이면 아무것도 안 하고 끝낸다. 달력을 cron에 넣지
않은 이유다.

### 넷이 각각 하는 일

**① 08:00 일일 배치 (`run_daily_ingest.py`)**
전 종목의 시세와 수급을 받아 데이터베이스에 넣고, 점수를 계산한다. 첫 실행은 과거
450일치를 받느라 15분쯤 걸리고, 그다음부터는 하루치만 더하니 훨씬 짧다.

**② 14:30 매매 사이클 (`run_cycle.py`)**
이 시스템의 본체다. 6단계를 차례로 밟는다 — 후보 선별 → 데이터 수집 → 결정 →
리스크 검증 → 주문 → 기록. 자세한 내용은 `docs/03-architecture.md`에 있다.

`--live`를 붙이면 실제 주문을 내고, 안 붙이면 **"이랬을 것이다"까지만 계산하고 멈춘다.**
지금은 안 붙어 있다. 판단 과정은 실제와 똑같이 돌면서 주문만 안 나간다.

**③ 장중 30분마다 감시 (`run_watch.py`)**
보유 종목의 손절 예약이 증권사에 제대로 걸려 있는지 확인한다. 빠져 있으면 다시 건다.
보유가 없으면 즉시 끝난다.

**④ 16:00 백업 (`ops.backup`)**
데이터베이스 전체를 파일 하나로 떠서 `/var/backups/alphaloop`에 둔다. 14일치만 남기고
오래된 건 지운다.

### 결과는 어디에 남는가

각 프로그램이 화면에 뿌리는 글자가 `/var/log/alphaloop/` 아래 파일로 쌓인다.

```bash
tail -50 /var/log/alphaloop/cycle.log    # 사이클이 뭘 했는지
tail -20 /var/log/alphaloop/ingest.log   # 배치가 잘 돌았는지
```

로그는 매일 회전한다 — 하루치씩 따로 보관하고, 14일이 지나면 지운다. 안 그러면 로그가
디스크를 다 먹는다.


## 11.10 배포 — 코드가 서버에 닿는 길

**배포란 내가 쓴 코드를 실제로 도는 곳에 옮기는 일이다.** 이 프로젝트는 git을 가운데
두고 세 곳이 연결돼 있다.

```
   개발용 맥                GitHub                    받아 가는 곳
   ─────────                ──────                    ────────────
   코드 수정
   pytest 통과 확인
   git commit
   git push      ─────────▶ 저장소 갱신 ─────┬──────▶ Vercel (자동, 화면)
                                            │
                                            └──────▶ NCP 서버 (수동, git pull)
```

**Vercel은 자동이다.** GitHub에 연결돼 있어서, 밀어 올리는 순간 알아서 새 화면을 만든다.

**서버는 수동이다.** 서버에 들어가서 직접 받아 와야 한다.

```bash
cd /opt/alphaloop
git pull origin main
```

일부러 수동으로 뒀다. 자동이면 코드를 밀어 올린 순간 매매 중인 프로그램이 바뀔 수 있는데,
그건 위험하다. `docs/10-operations.md` 10.12가 배포 시각을 사이클 사이(11:00~13:00)나
장 마감 후로 제한한 이유도 같다.

### `/etc` 아래 파일은 git pull로 안 바뀐다

한 가지 함정이 있다. cron 지시서·로그 회전 설정·API 서비스 지시서는 **저장소에도 있고
`/etc` 아래에도 있다.** `git pull`은 저장소 쪽만 바꾼다. 실제로 적용하려면 복사해야 한다.

```bash
cp ops/deploy/alphaloop.cron /etc/cron.d/alphaloop
```

절차는 `ops/deploy/README.md`에 정리돼 있다.

### 실거래를 켜고 끄는 것도 여기다

`--live`는 **코드 안에 없다.** cron 지시서에 적힌 명령줄 옵션이다. 그래서 켜고 끄는 데
코드 수정도, git도, 배포도 필요 없다. 서버에서 `/etc/cron.d/alphaloop` 한 줄만 고치면
다음 사이클부터 바로 적용된다.

```bash
# 끄기 — 계획만 내고 주문은 안 낸다
sed -i 's|run_cycle.py --live|run_cycle.py|' /etc/cron.d/alphaloop

# 켜기 — 실제 주문을 낸다
sed -i 's|run_cycle.py |run_cycle.py --live |' /etc/cron.d/alphaloop

# 지금 어느 쪽인지 확인
grep run_cycle /etc/cron.d/alphaloop
```

저장소의 `ops/deploy/alphaloop.cron`은 **드라이런이 기본값**이다. 이 파일을 다시 복사해도
실거래가 저절로 켜지지 않게 하려는 것이다. 켤 때는 항상 사람이 직접 `--live`를 붙인다.

### 왜 이렇게 하는가

코드를 그냥 복사해서 옮길 수도 있다. git을 쓰는 이유는:

- **되돌릴 수 있다.** 뭔가 잘못되면 이전 상태로 한 줄에 돌아간다.
- **서버와 내 맥이 같은 코드라는 걸 확인할 수 있다.** `git log`로 어느 시점 코드가
  돌고 있는지 언제든 안다.
- **무엇을 왜 고쳤는지 남는다.** 몇 달 뒤 과거의 나에게 물어볼 수 있다.


## 11.11 하루의 흐름

평일 하루 동안 실제로 일어나는 일을 시간 순으로 본다.

| 시각 | 무슨 일이 | 어디서 |
|---|---|---|
| 08:00 | 전 종목 시세·수급을 받아 점수 계산 | 서버 → 데이터베이스 |
| 09:00 | 한국 장 개장 | — |
| 09:00~15:25 | 30분마다 손절 예약 점검·트레일링 반영 | 서버 → 증권사 |
| 14:25 | 사이클 직전 정리 — 체결된 손절을 장부에 반영 | 서버 → 증권사 → 데이터베이스 |
| **14:30** | **매매 판단 6단계** | 서버 → 증권사 → 데이터베이스 |
| 15:20~15:30 | 마감 동시호가 | — |
| 15:30 | 장 마감 | — |
| 15:35 | 마감 정리 — 동시호가에서 체결된 손절을 장부에 반영 | 서버 → 증권사 → 데이터베이스 |
| 16:00 | 데이터베이스 백업 | 서버 |
| 아무 때나 | 대시보드로 결과 확인 | 브라우저 → Vercel → 서버 |

**14:30에 판단을 모은 이유**는 `docs/03-architecture.md` 3.1에 있다 — 그 시각이면 외국인·
기관의 순매수가 어느 정도 굳어 있고, 마감 직전 동시호가의 노이즈는 피할 수 있다.

**14:30부터 다음 날 09:00까지 18시간 30분은 시스템이 아무것도 못 하는 구간이다.** 그래서
손절을 증권사에 **미리 예약**해 둔다. 내가 자는 동안 값이 떨어지면 증권사가 알아서 판다.
이게 이 시스템에서 가장 중요한 안전장치이고, 아직 실계좌에서 검증되지 않은 부분이다.


## 11.12 문제가 생기면

### 어디를 먼저 보는가

```bash
# 1. 프로그램이 도는가
systemctl status alphaloop-api

# 2. 사이클이 뭘 했는가
tail -50 /var/log/alphaloop/cycle.log

# 3. 데이터가 들어왔는가
sudo -u postgres psql -d journal -c "select count(*) from daily_scores"

# 4. 디스크·메모리가 남았는가
df -h / ; free -m
```

### 어떻게 멈추는가

급한 순서대로.

| 상황 | 방법 |
|---|---|
| 주문만 멈추고 싶다 | `/etc/cron.d/alphaloop`의 사이클 줄에서 `--live`를 지운다 |
| 사이클을 아예 멈추고 싶다 | 그 줄 맨 앞에 `#`을 붙인다 |
| 전부 멈추고 싶다 | `/etc/cron.d/alphaloop` 파일을 지운다 |
| 대시보드만 멈추고 싶다 | `systemctl stop alphaloop-api` |

**멈춰도 데이터는 안 사라진다.** 데이터베이스는 별개로 돌고 있고, 백업도 남아 있다.

### 알림

문제가 생기면 Discord로 알림이 온다.

- 매매 전체 정지(SafeStop)
- 사이클 실패
- 일일 배치 실패
- **손절이 안 걸린 채 보유가 생겼을 때** — 가장 중요한 알림이다

또 `healthchecks.io`가 "정해진 시각에 신호가 안 왔다"는 것 자체를 감지한다. 서버가 통째로
죽으면 서버가 알림을 보낼 수 없으니, 바깥에서 지켜보는 눈이 따로 필요하다.


## 11.13 지금 상태와 남은 일

2026-09-07 기준.

**돌고 있는 것**

| 무엇 | 어디 | 상태 |
|---|---|---|
| 코드 | 서버 `/opt/alphaloop` | 배포됨 |
| PostgreSQL | 서버 | 표 19장 |
| cron 4종 | 서버 | 등록됨 (**사이클은 주문 없이 계획만**) |
| 조회 API | 서버, 상시 기동 | 정상 |
| 대시보드 화면 | Vercel | 배포됨, 로그인 동작 |

**아직 확인 못 한 것**

- **실계좌 연결** — 증권사 실전 API로 잔고를 한 번도 조회해 보지 않았다
- **손절 예약(`ORD_DVSN=22`)** — 모의투자가 이 기능을 지원하지 않아서, 실계좌 소액으로만
  확인할 수 있다. `ops/smoke_stop.py`가 그 확인용 도구다

**알고 있는 구멍**

- **트레일링 손절이 증권사에 반영되지 않는다.** 값이 오르면 손절선도 따라 올려야 하는데,
  지금은 데이터베이스에만 올리고 증권사에 걸린 예약은 그대로다. 처음 걸어둔 손절은
  정상이라 큰 손실은 막지만, 이익을 지키는 기능은 작동하지 않는다.
  정정 API(`TTTC0013U`)를 구현해야 한다.
- **계좌에 국내 매매와 무관한 자산이 있으면** 서킷브레이커가 잘못 발동할 수 있다.
  손익률을 계산할 때 분모(전일 총자산)에는 그 자산이 들어가는데 분자(현재 평가액)에는
  안 들어가기 때문이다. 계좌를 이 시스템 전용으로 비워 두는 것이 가장 깔끔하다.

**순서**

1. 계좌를 비운다 (국내 매매와 무관한 보유 정리)
2. 소액을 넣고 실계좌 연결을 확인한다
3. `ops/smoke_stop.py`로 손절 예약이 실제로 걸리는지 확인한다
4. 트레일링 손절 구멍을 메운다
5. 그다음에 `--live`를 켠다
